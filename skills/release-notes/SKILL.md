# Release Notes

指定されたGitHubリポジトリを解析し、利用者向けのリリースノートを単一のHTMLファイルとして生成する。

## Requirements

- 実行時にGitHubリポジトリのURLを指定する。
- Publicリポジトリと、認証情報によってアクセス可能なPrivateリポジトリを対象とする。
- Privateリポジトリにアクセスできない場合は、その理由を報告する。
- GitHub上のReleaseやリポジトリの内容を変更しない。
- 出力は単一のHTMLファイルとする。

## Workflow

### 1. Repository Analysis

指定されたリポジトリにアクセスし、以下を確認する。

- リポジトリの概要とプロジェクト構成
- Releasesとタグ
- 対象Releaseの変更範囲
- コミット履歴
- マージ済みPull Requests
- 関連するソースコードや設定ファイル
- 既存のREADMEやリリースノート

対象Releaseが指定されていない場合は、最新の安定版Releaseを対象とする。

情報が取得できない場合は、推測で補完せず、取得できなかった内容を明示する。

### 2. Change Analysis

Release間の変更を比較し、利用者にとって重要な変更を抽出する。

優先する情報:

- 新機能
- 追加されたコマンドやAPI
- 利用方法の変更
- 動作環境や依存関係の変更
- インストール方法や配布形式の変更
- 互換性に影響する変更
- 利用者が認識すべき修正

内部実装の変更、開発環境の変更、CI設定など、利用者に直接関係しない情報は原則として掲載しない。

コミットメッセージやPull Requestのタイトルだけで判断せず、必要に応じてソースコードを確認する。

### 3. Content Generation

既存のREADMEや過去のリリースノートがある場合は、プロジェクトの表現や構成を参考にする。

記載内容は第三者・利用者の視点で整理する。

- 概要は項目ごとに箇条書きにする。
- CLIコマンドは表形式で掲載する。
- CLIコマンドは複数のコマンドをまとめず、1コマンドにつき1項目とする。
- APIや利用方法は、必要に応じて表形式で整理する。
- インストール方法や実行例は、対象プロジェクトに該当する場合に掲載する。
- 動作要件は表形式で整理する。
- 配布ファイルがある場合は、プラットフォームとファイル名を対応させる。
- 関連Pull Requestや内部的な修正一覧は原則として掲載しない。

情報が存在しないセクションは無理に追加しない。

### 4. HTML Generation

以下の条件を満たすHTMLファイルを生成する。

- HTML5
- UTF-8
- CSSはHTML内に記述する。
- 外部ライブラリや外部CSSに依存しない。
- JavaScriptは原則として使用しない。
- PCとモバイルの両方で読みやすいレスポンシブデザインにする。
- 見出し、表、コードなどを適切に使い、情報を整理する。
- GitHub Releaseへのリンクを掲載する。

### 5. Validation

生成したHTMLを確認する。

- HTMLの構文が正しいこと
- 必要な情報が欠落していないこと
- コマンドやバージョンがソース情報と一致していること
- リンク先が正しいこと
- 表や箇条書きの内容に矛盾がないこと
- 利用者に関係しない内部情報が含まれていないこと
- 外部ファイルに依存せず単独で表示できること

誤りがあれば修正し、再確認する。

## Output

- リリースノートを単一のHTMLファイルとして出力する。
- ファイル名にはリポジトリ名とReleaseのバージョンを含める。
- 同じバージョンのHTMLを再生成する場合、既存ファイルを上書きせず、別の版として保存する。
- 生成したファイルへのリンクを提示する。
- 解析結果と生成内容について、必要な範囲で簡潔に報告する。

## Restrictions

- GitHub Releaseの作成・更新・削除を行わない。
- リポジトリのファイルやブランチを変更しない。
- コミットやプッシュを行わない。
- 確認できない機能や変更内容を推測で記載しない。
- 内部実装の変更を利用者向けの機能として誤って紹介しない。
